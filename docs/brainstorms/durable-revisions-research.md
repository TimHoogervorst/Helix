# Durable Revisions: storage research

Date: 2026-10-15

Status: completed research supporting the confirmed [storage resolution](https://github.com/TimHoogervorst/Helix/issues/684#issuecomment-6192540750) in [Explore standalone Mods over durable scientific data](https://github.com/TimHoogervorst/Helix/issues/681). That resolution is the canonical decision; this note retains the evidence, alternatives and implementation considerations. It is not an implementation specification or a claim that the target model is implemented.

## Recommendation

Keep one current record per Entity or Notebook Entry and store immutable, complete snapshots of each declared Revision Group in a separate platform-owned history table in the same database. Generalize the existing ELN ContentVersion approach. A Revision remains history belonging to a Durable Record, not another Entity. This is a design inference from Helix's existing model and the sources below, not a universal performance result.

**History storage and current-record ownership are distinct concerns.** The subsequent resolution selects concrete Platform Entity storage based on the existing Entity model; its Schema association, Source and identity concepts remain the starting point. Keeping a Mod's tables after removal does not preserve its Python models or readers. A platform-owned history table alone cannot guarantee access to all current Recorded Values without that Mod; the adoption decision must establish that access while preserving existing tables.

## Existing implementation

- [AbstractEntity](../../src/helix_core/abstracts.py) is an abstract Django base declaring common fields, including name, author, status, Project, Schema, properties and Source through inheritance. It standardizes behavior and fields; it is not a shared concrete record table. [Entity](../../src/bundled/lims/models.py) uses `lims_entity`; [NotebookEntry](../../src/mods/eln/models.py) uses `eln_entry` and adds document `content`.
- [ContentVersion](../../src/mods/eln/models.py) already stores separate full JSON snapshots, content hash, per-entry version number, author, time and save mode. Its unique constraint is `(entry, version_number)`. Both its entry and author foreign keys use `CASCADE`.
- [ELN's save path](../../src/mods/eln/views.py) saves current content, runs [content synchronization](../../src/mods/eln/sync.py), then snapshots the resulting content and hash. Title/status-only changes do not intentionally create document history. Initial creation does **not** create a ContentVersion; the first update containing content establishes version 1. [Existing tests](../../src/mods/eln/tests/test_content_version.py) explicitly cover that behavior and deletion of history with its entry.
- The implementation calls snapshots immutable, but the inspected model/migrations contain no update prohibition. Its next-version helper reads the latest row and adds one. The view has no transaction enclosing the whole save/sync/snapshot operation or `select_for_update`. The transaction inside `Sourceable.save()` protects that save and Source changes only. No `ATOMIC_REQUESTS` setting was found in [settings](../../src/server/config/settings.py), and [ActionLoggingMixin](../../src/helix_core/actions/mixins.py) adds no surrounding transaction. These are static findings, not a reproduced concurrency failure.
- `content_changed` compares incoming content before synchronization, while the persisted snapshot is taken afterward. A normalization that maps different input back to the existing committed value could therefore produce redundant history. Snapshotting after synchronization is already correct; change detection should ultimately use that same final representation.
- [Identity migration 0010](../../src/mods/eln/migrations/0010_identity_fields.py) rewrites historical `ContentVersion.content` without recomputing `content_hash`. Where that transformation changes a value, it conflicts with strict payload immutability and hash consistency. Future migrations must preserve the original historical representation and its interpretation, or explicitly distinguish a transformed representation. No migration repair is attempted here.

The [domain glossary](../../CONTEXT.md#durable-scientific-data) defines Revision Groups, exact contract bindings, and Mod-independent preservation as target requirements. It explicitly distinguishes the general Revision concept from ELN ContentVersion. Generalizing history need not redefine what an Entity is.

## Alternatives and precedents

| Design | Implications for Helix | Assessment |
| --- | --- | --- |
| Current record plus separate full snapshots | Ordinary browsing reads one current row. History lookup retrieves a self-contained group state. Current content is duplicated in its latest snapshot. Both writes must commit together. | Best starting fit; already used by ELN. |
| Immutable states plus a head pointer | One stable identity row points to the current version; current reads join/load its state. Avoids duplicating the current payload, but changes existing query and save paths. | Valid design, larger migration; no evidence it is needed now. |
| Mix current and historical rows in Entity tables | Every listing/count must select the current state; references must distinguish record identity from state identity. Existing single-row primary keys and foreign keys need redesign. | Poor fit for the requested continuity. |
| Deltas or event history | Smaller changes may store less, but reading a state depends on a base and reconstruction. Events also require retained interpretation logic; JSON deltas and domain events are distinct designs. | Defer until measured storage pressure justifies reconstruction complexity. |

`django-simple-history` creates separate historical tables and records model fields plus metadata. `django-reversion` stores serialized model instances in Version rows grouped by a Revision. These are primary-source precedents for separate snapshots, not recommendations to adopt either package unchanged. Reversion documents that deserialization/revert can fail when the stored data is incompatible with the current database schema; Helix needs retained Data Contracts and generic readers rather than relying on today's Django models. [Simple History quick start](https://django-simple-history.readthedocs.io/en/latest/quick_start.html#what-is-django-simple-history-doing-behind-the-scenes), [Reversion API](https://django-reversion.readthedocs.io/en/stable/api.html#reversion-models-version).

Microsoft's event-sourcing guidance describes state reconstruction from events, concurrency/versioning concerns, and snapshots to bound replay work. **Inference:** requiring old Mod code to replay scientific Actions would work against Helix's preservation goal. Full saved values avoid that particular dependency. [Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing).

## Proposed shape and indexes

A platform Revision would identify its Durable Record and Revision Group, have its own immutable identity and per-group number, and retain complete group values, exact contract bindings, provenance, actor attribution, time and a canonical content hash. Group identity and contract bindings must participate in change detection: identical JSON under a changed scientific contract is not automatically the same state. The precise identity linkage and group declaration API remain open.

Use a unique B-tree constraint on `(record_id, group_key, version_number)`. If record identity remains a typed pair, include both components instead of assuming IDs are globally unique. This supports uniqueness and lookup of the latest/history rows for one group. PostgreSQL's unique constraint creates an index; leading equality keys narrow a multicolumn B-tree scan, and backward scans support descending version order. Do not automatically add a duplicate descending index. [Constraints](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS), [multicolumn indexes](https://www.postgresql.org/docs/16/indexes-multicolumn.html), [index ordering](https://www.postgresql.org/docs/16/indexes-ordering.html).

Consequently, ELN's existing `(entry, version_number)` uniqueness constraint already supplies the main history-access index. For history lists, fetch metadata with cursor pagination; retrieve a complete payload only when inspecting a particular Revision. A content hash needs no separate index merely to compare against the latest row.

Django uses PostgreSQL `jsonb` for JSONField. Add a GIN or expression index only for a concrete query *inside* historical content; retrieving a snapshot by its record/group/version does not need one. A broad GIN index stores entries for keys and values, whereas targeted expression indexes can be narrower. [Django JSONField](https://docs.djangoproject.com/en/5.1/ref/models/fields/#jsonfield), [PostgreSQL JSON indexing](https://www.postgresql.org/docs/16/datatype-json.html#JSON-INDEXING).

A Django GenericForeignKey is not equivalent to a foreign key to a single record table: its composite lookup index must be declared, and a deleted target can leave the stored identifiers with a null resolved object. Choose this linkage deliberately rather than treating it as durable referential integrity. [Django generic relations](https://docs.djangoproject.com/en/5.1/ref/contrib/contenttypes/#generic-relations).

## Growth and operational limits

History grows with committed group changes. Separate tables keep normal record queries separate from history queries, but do not eliminate database storage, backup, WAL, or index costs. Estimate workload as revision count multiplied by measured stored snapshot size, then measure index/TOAST overhead and write costs. There is no Helix benchmark or reliable capacity threshold in this research.

PostgreSQL TOAST compresses and/or stores large values outside their main rows; it does not make repeated full snapshots free or provide application-level cross-revision deduplication. A TOAST-able value has a logical size limit of about 1 GB, which is a ceiling, not an acceptable payload target. Large attachments should have stable references to separately retained bytes instead of copying bytes into every document snapshot. The attachment lifetime must include all retained referencing Revisions. [TOAST](https://www.postgresql.org/docs/16/storage-toast.html).

Start without partitioning. Revisit it using actual table/index sizes, latency and retention needs. PostgreSQL partitioning has maintenance and query-planning trade-offs, and unique constraints on partitioned tables must include every partition key. Time partitioning therefore complicates global `(record, group, version)` uniqueness. Do not introduce it merely because a table will grow. [Table partitioning](https://www.postgresql.org/docs/16/ddl-partitioning.html).

PostgreSQL's transient row versions are not durable scientific history: vacuum reclaims obsolete row versions. Explicit retained Revision rows are required. [Routine vacuuming](https://www.postgresql.org/docs/16/routine-vacuuming.html).

## Save correctness and immutability

Proposed save boundary: load/lock current state, check the submitted base Revision, validate and normalize the proposed values, compare each final group state, update current data and append changed group snapshots in one transaction. Create the initial snapshot when the group first receives its committed value. Include exact definitions and any required scientific provenance in that operation; a best-effort activity log is not the preservation mechanism. [Django transactions](https://docs.djangoproject.com/en/5.1/topics/db/transactions/).

Lock a stable parent record or group-head row, including when no history exists, before allocating a number. Locking only the latest Revision cannot protect an empty history. A uniqueness constraint catches duplicate numbers but does not itself serialize allocation. PostgreSQL row locks coordinate competing writers; Django exposes them with `select_for_update()`. SQLite does not implement that locking behavior, so PostgreSQL concurrency tests are needed. [PostgreSQL locking](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS), [Django locking](https://docs.djangoproject.com/en/5.1/ref/models/querysets/#select-for-update).

Serialization alone does not detect a stale browser replacing newer content: compare the submitted base Revision inside the transaction and reject or explicitly resolve conflicts. ELN's user-facing EntryLock does not protect against concurrent requests from the same user. This is a proposed concurrency policy, not a claim that such a failure has been reproduced.

Make history append-only through the platform API and prevent arbitrary mutation through ORM/admin paths. For stronger database enforcement, PostgreSQL privileges and triggers can prohibit payload updates. Define permitted owner deletion separately so immutability enforcement agrees with retention policy. Database owners/administrators remain a different trust boundary; a hash is not by itself tamper prevention. [PostgreSQL privileges](https://www.postgresql.org/docs/16/sql-grant.html), [triggers](https://www.postgresql.org/docs/16/sql-createtrigger.html).

## Confirmed deletion policy and migration considerations

The user explicitly defers archive behavior. [ADR 0026](../adr/0026-source-replaces-containment.md) currently deletes Source subtrees, and ELN cascades deletion to its history. **Confirmed interim rule:** an authorized hard deletion removes the record and its Revisions together. This is independent of choosing a separate table. Retaining history after removing its owner instead would require retained identity, access rules, and orphan-history presentation; it is not a free side effect of table separation.

The confirmed policy leaves surviving exact references to deleted scientific inputs unavailable; they never silently follow a current value or replacement record. No new reference-based deletion blocking or archive rule is introduced.

Actor deletion is a distinct concern: `ContentVersion.created_by` and `AbstractEntity.author` both cascade today, so account deletion can remove history directly or through its record. The confirmed target preserves scientific records/history and recorded attribution when an account is deleted; the live account link may become empty. Changing only the Revision author FK does not address the owner-record cascade.

For ELN adaptation, preserve its useful full-snapshot and post-sync behavior while moving history responsibility into the platform, adding initial snapshots, final-state change detection, safe concurrent numbering, atomic current/history writes, and enforced payload immutability. Preserve existing version identities/references if data is migrated; if only current values exist, mark a migration baseline rather than inventing lost historical states. Exact contract versions for old snapshots must be established from evidence, not guessed.

Validation for a later implementation should cover initial creation, unchanged normalized input, title-only changes, grouped-field changes, contract-binding changes, rollback on snapshot failure, concurrent/stale saves on PostgreSQL, immutable payloads, actor deletion, owner deletion, and inspection with the original Mod absent. No implementation or benchmark tests were run for this research-only note.

## Existing Activity Feed and proposed Revision integration

Follow-up inspection during the storage discussion found the existing history-like block is the Activity Feed. The shared [Activity component](../../src/shell/src/shared/components/Activity.tsx) and [hook](../../src/shell/src/shared/hooks/useActivity.ts) render persisted Action Log Entries with pagination and expandable request-ID grouping. ELN and LIMS supply thin subject bindings. ELN's [action endpoint](../../src/mods/eln/views.py) reads Platform ActionLogEntry rows for the Entry, not ContentVersion rows. The separate History button in [ElnChrome](../../src/mods/eln/workspace/ElnChrome.tsx) is explicitly a placeholder; the inspected feed has no historical snapshot viewer or diff.

[useActionAccumulator](../../src/shell/src/workspace/TipTapRenderer/useActionAccumulator.ts) accumulates block changes and posts audit events after a successful save, using a shared request ID for grouping. Multiple block events can describe one document ContentVersion. ContentVersion snapshots the whole saved document, including its block content, rather than versioning each block independently. [ADR 0025](../adr/0025-pending-indicator-over-optimistic-activity.md) requires persisted-only feed rows and an unsaved-changes indicator.

The [ActionLogEntry model](../../src/helix_core/models.py) already has optional version-reference, version-ID, label and hash fields. ELN's save path supplies them for its entry-level log when that log is emitted. However, [ElnActionSerializer](../../src/mods/eln/serializers.py) does not expose those dedicated fields, the shared frontend ActionItem has no typed revision association, and the post-save block-event path does not establish a reliable link to the saved ContentVersion.

Confirmed adaptation: retain the shared Activity Feed and its subject boundary; expose Platform record activity with explicit affected-group Revision associations; add read-only access to those exact saved states. Several block events may link to one document Revision, while one Action may affect multiple groups or records. Metadata-only Actions remain visible without inventing a content Revision. Do not infer associations from timestamps, request IDs alone, or whichever Revision is latest when a delayed audit POST arrives. Revision links must originate from the committed write result, with durable linkage handled by the Action execution design.

ELN acceptance example: editing a paragraph and a table in one successful save creates one document Revision containing both saved changes. The activity group retains both descriptions and opens that exact document Revision. A title-only edit adds activity without a new document Revision. A multi-group Entity's historical viewer must label the selected group; unrelated current fields must not be presented as a complete historical record snapshot. Exact UI layout and comparison tools belong to the Block prototype decision. No UI or backend implementation was changed by this inspection.
